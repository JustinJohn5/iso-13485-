# 文件集关联检查设计

编制日期：2026-11-23。本文是后续功能设计，不是已上线功能说明，也不是 ISO 13485 标准原文。

## 1 当前能力与下一步

当前网页可批量上传、识别文件类型、手动修正类型、逐份运行文本规则，并对相同内容同类型去重计分。自动类型用于选择适用规则，尚未建立手册、程序、表单和记录的关系。

后续将检查单位从“本次文件队列”升级为“审核项目中的体系文件集”。同一个项目可分批补充文件，按指定审核日期、范围和记录期间生成可追溯快照。一次只提供质量手册也可以开始建档；引用的程序或记录未上传时列为“本次未提供”，保留待补充位置。

## 2 分开文件层级与业务主题

当前类型把“程序文件”和“管理评审”等放在同一列表，适合初步筛选，不能直接作为长期关联模型。后续保留旧字段兼容，并增加两个独立维度：

| 维度 | 示例 | 用途 |
| --- | --- | --- |
| 文件层级 | 质量手册、程序文件、作业指导书、表单模板、已填写记录、其他 | 区分承诺、实施方法、采集载体和执行证据 |
| 业务主题 | 文件控制、采购、内部审核、管理评审、风险管理等，可多选 | 把同一过程的不同层级文件归到一起 |

例如，“管理评审程序”是程序文件，“管理评审记录表”可能是空白模板，“2026 年管理评审记录”才可能包含执行证据。名称含“记录”不能直接判定为已填写记录；必须检查填写内容、日期、参与者、结论等，并允许人工确认。

## 3 建立有证据的引用链

基本方向为：质量手册 → 程序文件 → 表单模板 → 已填写记录。也允许手册直接引用记录、程序相互引用、一份记录同时支撑多个要求。关系是多对多，不强制拼成单一路径。

以下编号、期限和职责都是演示数据，以用户实际文件规定为准：

| 来源要求 | 对应文件 | 对照内容 | 输出示例 |
| --- | --- | --- | --- |
| 手册写“按 QP-07 采购控制程序执行” | QP-07 当前适用版本 | 编号、名称、版本及适用范围 | 已关联；或版本待确认 |
| QP-07 要求质量部评价供应商 | 供应商评价表模板 QR-07-01 | 职责、评价字段、批准要求 | 模板字段覆盖；或字段待补充 |
| QP-07 规定每年复评 | 指定期间的供应商复评记录 | 日期、供应商、评价结果、批准及后续措施 | 本次已提供证据；或本次未提供该期间记录 |
| 复评记录显示需整改 | 整改及验证记录 | 对象、责任人、期限、关闭依据 | 已找到跟进；或证据待补充 |

手册与程序职责相反时形成“内容冲突待核实”；模板存在但没有已填写记录时，只能说明存在记录载体，不能说明过程已实施。

## 4 四层对照与状态

1. 单份文件：标识、版本、批准、日期、相关章节等基础线索。
2. 引用关系：被引用文件能否在本项目找到，编号、标题、版本、日期是否匹配。
3. 内容一致性：手册承诺是否由程序承接，职责、频次、保存期限、审批角色和适用范围是否存在矛盾。
4. 执行证据：程序要求的记录，在指定期间、样本和业务对象内是否提供，能否串联执行、结果和跟进。

结果使用明确状态：已关联、候选待确认、版本冲突、本次未提供、无法提取、内容冲突待核实、不适用待确认。任何一份文件抽取失败都不能静默当作不存在。

“本次未提供”与“企业不存在该文件”含义不同。未找到引用对象先列补件清单，不直接作为企业不符合项；审核人员确认范围、文件清单和补件后，再决定是否形成正式发现。

## 5 引用匹配及版本规则

- 优先按文件编号精确匹配；编号归一化处理全半角、空白和常见分隔符，同时保存原始写法。标题同义词或相似度只生成候选，不能自动覆盖编号冲突。
- 明确写了版本号的引用，优先匹配该版本；没有写版本的引用，按审核日期和受控文件清单解析适用版本，不能单凭上传时间认定“最新有效”。
- 同编号多版本并存时保留全部原件和版本记录，标识现行、历史或待确认；不自动覆盖、删除旧版。一份历史记录可能合法使用当时有效的旧模板，应按记录日期核对。
- 相同原始内容可复用解析产物；同编号不同内容必须提示版本或内容差异，不能按同名文件去重。当前实现的 SHA-256 去重仅覆盖本次完全相同的文件字节。
- 文件名、封面标题、正文引用互相矛盾时保留候选和理由；由用户修正，不在不确定时强行连线。
- 循环引用、孤立文件、模糊简称、缺少版本和无法确定的引用位置单列提醒，避免循环处理或错误关联。

## 6 原文定位和数据模型

当前抽取文本不足以直接提供可靠的页码跳转，后续须保存结构化片段：PDF 页码、DOCX 段落/表格坐标、XLSX 工作表与单元格、TXT 行号。DOCX 本身没有稳定排版页码，不应编造页码；需要页码时另行渲染并保留对应产物版本。

建议仍统一存入既有 MySQL 8.4，原件保存在受限存储目录：

| 实体 | 主要内容 |
| --- | --- |
| 审核项目及文件集 | 组织/场所、产品范围、审核日期、记录期间、成员权限 |
| 逻辑文档与版本 | 编号、标题、层级、主题、修订、生效/作废日期、状态、原件摘要 |
| 内容片段 | 标题路径、原文、定位锚点、抽取版本、置信度 |
| 引用与关联 | 来源版本及片段、目标编号/版本、候选、关系类型、确认人和确认时间 |
| 要求与记录证据 | 职责、频次、保存期限、业务对象、记录期间、原文依据 |
| 审核快照与发现 | 本次使用的文件版本、规则/模型版本、对照结果、证据双方定位、人工复核结论 |

补件或修改分类后仅重新分析受影响的关系，历史审核快照不被新文件改写。数据库结构变更先编写迁移并在 `_codextest` 验证，再按部署流程应用。

## 7 网页操作与报告

建议新增“审核项目 → 文件清单 → 关联对照 → 补件清单”流程：

1. 建立项目并填写审核范围、基准日期和记录期间。
2. 分批上传手册、程序、模板和记录；显示自动层级、主题、编号、版本，允许批量确认与逐项修正。
3. 系统生成引用候选；用户确认歧义和适用版本后运行关联检查。
4. 主界面显示对照矩阵，点击每一格可同时查看来源与目标的原文和位置。
5. 补件后仅重算相关项；导出时注明范围、样本、未提供材料、规则版本及人工复核状态。

核心矩阵列为：手册要求｜程序依据｜模板要求｜实际记录｜缺口/冲突｜双向证据位置｜复核状态。还可提供关系图辅助导航，矩阵承担主要复核工作。

## 8 分阶段落地与验收

第一阶段先做审核项目、文件层级/主题、编号版本提取、引用核对和补件清单。验收重点是分批补件、编号候选歧义、同号多版本、历史模板、跨用户数据隔离及双向原文定位。

第二阶段做职责、频次、期限等结构化要素对照和冲突提示。只有文本表述等价但规则无法判断时，再考虑大模型辅助；保留双方原文、理由和人工复核，不能把模型推测当事实。

第三阶段做记录样本链路、报告导出和历史快照对比。实际执行有效性仍需结合业务现场和专业审核，文本系统不自动给出认证结论。

若引入大模型，按项目规范统一使用 OpenAI 兼容调用封装；地址、模型、参数和 API Key 通过有权限的网页管理，敏感值加密存储于后端配置，主密钥留在后端 `.env`。文档正文作为待分析数据，不能执行其中的指令；外发范围和脱敏策略需在产品流程中明确。
