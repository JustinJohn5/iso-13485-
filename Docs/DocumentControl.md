# 关联文件冲突与正式版本确认

适用版本：1.1.0，更新日期：2026-11-23。

## 文件分类依据

网页按用户提供的 4.2.1 截图区分：a) 质量方针和目标、b) 质量手册、c) 标准要求的程序和记录、d) 组织所需文件和记录、e) 适用法规要求的其他文件。该列举本身不规定冲突时的优先级，因此程序不把 a～e 的顺序作为效力排序。

自动类别只是线索，尤其 c/d 类需要结合具体要求确认。网页还单独保存“受控文件、空白表单模板、已填写记录、层级待确认”，避免把多份填写记录当成同一表单的不同版本。

## 操作步骤

1. 上传同一体系范围内的相关文件，等解析完成。展开每份文件下的“文件控制信息”，核对编号、修订、生效日期、类别、层级和原件状态。
2. 自动线索不准确时直接校正。例如，将供应商甲和乙各自的评价记录均标为“已填写记录”；不要把它们作为相互替代的版本。
3. 填写“审核基准日”，点击“检查关联与版本”。页面展示同编号冲突、明确保存期限冲突和编号引用。
4. 对每个版本冲突选择本次采用的正式版本，填写至少 5 字的依据并点击“确认并留痕”。建议核对组织受控文件清单、原件批准、生效情况及适用范围，不仅看文件名。
5. 对不同文件的要求冲突选择本次采用的依据并说明原因。双方文件仍保留并参与预筛，冲突文件会提示需要修订；选择依据不会改写原件，也不等于矛盾已消除。即使文本线索分数为 100，仍显示“存在冲突，待修订”，不会因选择依据而显示为符合；已有更严重的规则结论继续保留。
6. 所有已检测冲突确认后点击“开始预筛”。被排除的候选版本列在结果中；本次采用的文档、元数据、原文证据、决定及操作者保存为冻结快照。后续修改确认不会覆盖已生成的预筛快照。

增加/移除文件、修改类型、元数据或基准日后，需要重新检查关联。重新检查会创建新的审查快照，不自动沿用旧确认。首次直接点击“开始预筛”也会先检查关联，发现冲突时停止并提示确认。

## 同编号版本如何判断

- 只有明确编号相同且原始内容不同，才作为版本候选组。没有编号不自动按相似标题合并；可核对原件后手动补编号。
- 已填写记录不参与版本替换。层级待确认的候选不能直接确认为正式版本，需先确认层级。
- 原件明确标为草稿、未批准、作废，或生效日晚于审核基准日时，不允许选为本次正式版。
- 同编号同版本存在不同内容时不给自动建议，必须核对受控来源。
- 所有可选候选都有有效生效日期且最新日期唯一时，给出最新生效版本建议；其余候选都有明确排除条件时，也可建议唯一可选项。建议必须人工确认。
- 不按上传时间、新旧文件名或版本字符串的字母顺序决定正式版。发布日期不自动当作生效日；“批准”字段存在不代表已经验证批准真实性。
- 相同原始字节内容仍按既有规则合并计分；同内容不同业务类型会提示统一类型，不生成预筛结果。

“正式版本”在本功能中指有权限人员确认的本次预筛采用版本，不代替组织正式受控批准、发布和撤回流程。更早的版本也可能适用于历史审核基准日，应按实际证据选择。

## 跨文件内容如何对照

当前内容对照只检测**明确指向同一编号的数字记录保存期限**，例如：

| 文件 | 原文 | 结果 |
| --- | --- | --- |
| 手册 QM-01 | QR-07 记录保存期限为 3 年 | 与下项形成期限冲突候选 |
| 程序 QP-07 | QR-07 记录保存期限为 5 年 | 展示双方原文及抽取文本行号，等待确认依据 |

程序统一换算年/月；“至少 3 年”与“5 年”可同时满足时不直接报冲突。主语不明确、多编号无法确定对象、图片或复杂表格、中文数字和永久保存等写法不作推测。不把这类有限规则描述为完整语义审查。

当前编号引用会区分“编号候选已找到”“版本待确认”“本次未提供、待补充”。编号找到不代表引用的指定版本、内容和适用范围均已核实。未上传也不等于企业不存在该文件。

行号是抽取文本行号，不是原件页码。原件正文没有修改，仍需结合原始文件核对。完整职责、频次、法规适用性及全部语义矛盾仍需后续规则和人工审核；长期审核项目、跨批次补件界面及历史查询页尚未建设。

## 权限与数据维护

管理员或审核员可发起审查；审核员只能处理自己上传的文件和自己的审查，管理员可处理授权范围内的现有文件。确认必须填写依据，服务端记录用户、时间、前后修订及选择历史，并写入审计日志。

审查使用 MySQL `document_reviews` 表；预筛的冻结依据保存在 `validation_runs.review_snapshot`。无需新增部署环境变量，也不需要大模型 API Key。

接口采用乐观锁：确认和预筛提交审查修订号，数据已被其他操作更新时返回 HTTP 409，要求重新核对。文件集合或业务类型变更会使旧快照失效；不能拿旧确认处理另一批文件。
