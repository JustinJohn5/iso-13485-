# ISO 13485 文本生成与文件预筛规则总则

编制日期：2026-11-24。文档版本：1.0。状态：待业务复核，尚未实施。

本规则以项目新增的 ISO 13485:2016 中文资料为依据，重新规定文件如何生成、如何预筛及如何解释结果。当前交付仅为规则文档；运行中的规则包仍为 `iso13485-core` 1.0.1，模板、网页、接口、数据库和历史结果均未因本文修改。

## 1 文档组成与使用顺序

| 文档 | 用途 |
|---|---|
| 本文 | 来源、适用性、现状差距、文件映射和后续实施边界 |
| [文本生成规则](Iso13485GenerationRules.md) | 生成输入、编写要求、模板要求、模型约束和生成自检 |
| [文件预筛规则](Iso13485PrescreenRules.md) | 证据、判定状态、预筛流程、结果口径和验收案例 |
| [条款规则矩阵](Iso13485ClauseMatrix.md) | 第 4—8 章共 72 个末级条款的生成要素与预筛条件 |

先确定组织和产品的适用范围，再按矩阵选择需要的要求。一个条款可能由多份文件共同承载，一份文件也可能覆盖多个条款。不得把矩阵的 72 行解释成必须编制 72 份文件。

本次正文覆盖 4—8 章，另使用第 1 章确定适用边界、第 0.2 节区分要求与建议。第 2—3 章用于理解引用和术语；资料性附录 A、B、参考文献及“注”不自动转换为新的强制要求。

### 2.3 来源疑点的处理

1. 所提供译文的 7.5.6 首段陈述了过程输出无法由后续监视测量验证的情形，但表述不完整。将触发条件和任何拟补充的文字列为人工核对事项；不能静默补成“标准原文”并据此自动扣分。
2. 所提供译文的 8.5.3(d) 在预防措施条款中使用了“纠正措施”。矩阵概括为“核查措施的不利影响”，精确措辞须依据经组织确认的权威版本复核；疑点本身不作为组织文件缺陷。
3. 翻译、OCR、排版或编号存在歧义时，保存原文位置与疑点，停止该争议点的自动结论，其他无争议检查继续。经授权人员确认后，单独记录解释依据和规则版本。
4. 标准中的引用文件不自动变成“引用了旧版就失败”的禁用清单。区分注日期引用、非注日期引用、历史叙述和组织适用依据；是否需更新由组织结合受控外来文件和适用法规确认。

## 3 三类规则必须分开

| 类别 | 含义 | 典型例子 | 输出要求 |
|---|---|---|---|
| 标准要求 | 原件明确提出的要求，经适用性分析后使用 | 文件控制、管理评审输入、记录保存 | 必须标明具体条款及本地原件定位 |
| 项目管理约定 | 为便于本平台生成、归档、检索而增加的约定 | 独立文件编号、封面日期字段、字数、示例目录、权重 | 明示“项目约定”，不冒充 ISO 强制格式 |
| 人工核实事项 | 无法仅凭抽取文本证明的内容 | 批准真实性、执行有效性、法规适用、临床证据 | 列出取证对象和核实问题，不自动宣告符合 |

4.2.4 要求文件可识别、修订状态受控，不直接要求所有组织使用本项目的编号格式。批准字段存在、签名图像存在或出现“符合要求”均不能证明批准有效或实施符合。

标准允许文件结构按组织需要安排，不强制按标准条款顺序编排，也不强制每项过程都拆成独立程序。

## 4 适用性规则

### 4.1 生成和预筛共同需要的组织事实

| 事实组 | 应收集内容 | 未知时处理 |
|---|---|---|
| 组织和场所 | 组织名称、职能、活动、涉及场所、职责接口 | 保留“待确认”，不猜测制造商或经销商身份 |
| 产品和器械族 | 产品、型号、预期用途、类型、风险相关特性、组织确定的寿命期及依据 | 不编造产品分类、技术限值或寿命期 |
| 市场和法规 | 目标市场、管辖区、适用法规清单、版本及确认人 | 不预设国内或国外法规自动适用 |
| 生命周期活动 | 设计、采购、生产、清洁、包装、储运、安装、服务等实际范围 | 未知活动列为待确认，不视为不存在 |
| 特殊条件 | 无菌、植入、特殊环境、过程输出可验证性、软件应用 | 每个条件分别确认，不能由文件名推定 |
| 外部过程 | 外包项目、供方、责任分工、质量协议及监视安排 | 外包不等于本组织免除责任 |
| 文件用途 | 程序、计划、规程、报告、空白表单、已填写记录、支持资料 | 同一业务类型可有不同文件用途 |
| 审核上下文 | 单份文件或体系文件集、审核基准日、所选正式依据 | 未选择体系审查时不报全套缺件 |

现有网页尚不具备上述完整结构化输入。本表是后续规则落地的输入契约，不表示这些字段已经上线。

### 4.2 适用状态与审批

- **适用**：已有组织事实或法规依据表明需要执行。
- **待确认**：事实不足、依据不完整或存在争议。显示需确认原因，不能默认为“不适用”。
- **不适用且已确认**：有具体条款、理由、产品与活动事实、法规依据（涉及法规时）、确认人和时间；保存质量手册相应说明或引用。
- **本文件不承载**：要求由其他文件承担。只是检查路由，不等于条款对组织不适用。

对于第 6、7、8 章，按第 1 章所述条件逐项论证不适用理由；第 4、5 章不能套用这一通用理由整章排除。对于设计开发控制的删减，还需证明适用法规允许并在体系及声明中明确说明。仅填写“不涉及设计”不足以批准删减。

外包活动仍应纳入相应过程的控制要求；例如委托灭菌不能据此跳过外包监视和质量协议。特殊活动未发生或产品不具备特定属性，需要事实支持；对“不适用”的批准属于组织职责，不由模型自动完成。

## 5 对现有规则的修订方向

以下是文档提出的目标规则，当前系统仍按原代码运行。

| 现有规则或逻辑 | 核对结果 | 目标规则 |
|---|---|---|
| `DOC-001` 文件编号 | 特定编号格式属于项目管理约定 | 检查文件可识别性与受控清单关联；编号格式单独作为项目约定提示 |
| `DOC-002` 版本标识 | 有条款依据，但标识存在不足以证明状态正确 | 核查修订状态、选用依据和引用版本，不按字符串大小自动择新 |
| `DOC-003` 批准关键词 | 空审批栏、模板说明也会命中 | 区分批准安排、待填字段和已填写记录；真实性人工核实 |
| `DOC-004` 日期格式 | 特定封面字段属于项目约定，正则不能验证日期有效 | 校验真实日历日期与适用版本；未来计划日期不能一律报错 |
| `QMS-001` 范围关键词 | 未覆盖程序引用、过程关系和文件结构 | 扩展为 4.2.2 的要素组，删减理由按实际情况核对 |
| `MR-001` 输入和输出 | “输入”“输出”两个词不足以覆盖 5.6 | 逐项覆盖 5.6.1—5.6.3，区分程序与会议记录 |
| `AUD-001` 发现和跟进 | 缺策划、独立性、报告与及时跟进 | 覆盖 8.2.4 的过程安排、记录及跟踪验证 |
| `RISK-001` 风险关键词 | “剩余风险”等是细化方法，不能将其均声称为 7.1 原文要求 | 7.1 先检查文件化风险管理过程与记录；具体方法及术语按组织选择的适用依据检查 |
| 分数对应“符合”“不符合” | 容易把文本命中误解为正式审核结论 | 使用文本覆盖与待复核状态，禁止以分数替代审核结论 |
| 模板与 AI 各自维护要求 | AI 未获得条款对应要求，模板要素较简略 | 两者共用本文矩阵及文件用途，保持来源与版本可追溯 |
| 固定 20 项整套目录 | 是自有示例，缺项不等于标准缺件 | 根据组织适用性与条款承载关系确认所需文件及记录 |

## 7 共同数据与版本规则

1. 标准版本、来源文件摘要、规则文档版本、执行规则包版本、模板版本、文件版本和草稿修订分别记录。本文 1.0 不代表运行规则包升级。
2. 每个矩阵条款使用 `R-条款号` 标识。后续可细化为 `R-5.6.2-01` 等子规则；必须保留父条款、来源位置、适用条件、预期文件用途、生成要素和预筛条件。
3. 同一子规则的必需概念组必须与其生成要求对应。不得通过模板中预置关键词让尚未完成的文件自动通过。
4. 可组合承载的要素，须记录各证据所在文件；明确要求同一记录关联的数据不能用无关联文件拼接满足。相同内容重复上传不增加覆盖率。
5. 后续生成快照应固定采用的条款要求与事实来源；后续预筛应冻结规则版本、输入摘要、基准日、适用性判断、引用依据、结果和人工决定，避免新规则覆盖历史解释。
6. 本次不增加数据库字段、接口或模型配置。未来需要保存上述新增信息时，应另行评估兼容、迁移和独立测试副本验证。

## 8 后续实施和复核清单

本文不构成系统实施授权。待业务复核后，实施范围建议按以下顺序确认：

1. 由组织质量负责人确认原件解释疑点、适用性和条款矩阵；确认保存期限及市场法规依据。
2. 明确现有 20 项目录中每条要求的承载文件，决定是否需要新模板；细化规则字段与人工判定责任。
3. 将生成、预筛接入同一版本的规则目录；分别验证普通模板、整套生成和 AI 编写。
4. 增加文件用途、适用性、引用证据与待填项的判断；更新规则手册和结果解释。接口破坏性变更需另行确认。
5. 按预筛文档中的案例补齐测试，在 MySQL 8.4 测试副本执行涉及写入的验证；前端交互使用 Playwright。
6. 评估现有引擎的 `pass/fail/skipped` 与新判定状态的兼容方式，保留历史结果和旧规则解释；经发布授权后才部署新包。

本次核对仅涉及规则与编写链路，未实施项目整体重构。相关文件现状：`Rules/core.json` 仅有八条规则；`Rules/Checks.py` 以全篇关键词和正则为主；`Authoring/TemplateLibrary.py` 与 `ManualSuites/Catalog.py` 分别定义模板；`Authoring/AiDraft.py` 使用通用系统提示；`ScoringService.py` 使用符合性措辞。建议后续增加独立要求目录和解释模块，收益是减少生成与检查漂移、明确证据边界。是否拆分及如何迁移由实施方案确认。
